## 三、主要发现

### F16-1：静态死资产约 2.2MB 入库并随每次部署分发

`frontend/public/` 整体复制进 `dist/`，以下文件**无任何活动引用**却持续发布到生产：

| 文件 | 体积 | 状态 |
|---|---:|---|
| `ueditor/ueditor.all1.js` | 1.3MB | 全仓 grep 零引用（疑似 `ueditor.all.js` 的历史副本） |
| `ueditor/dialogs/contentimport/mammoth.browser.min.js` | 642KB | 仅被死文件 `contentimport.js` 引用；活动对话框 `contentimport.html` 不加载它 |
| `ueditor/dialogs/contentimport/showdown.min.js` | 75KB | 同上 |
| `ueditor/dialogs/contentimport/contentimport.js` + `.bak` | 60KB | 死代码（带 MathJax 的旧 showdown 管线，从未被活动 HTML 加载） |
| `ueditor/dialogs/contentimport/{_fixed,_original,_simple}.html` | 27KB | 死副本；活动对话框仅 `contentimport.html`（由 `ueditor.all.js` 的 dialogIframeUrlMap 注册） |

背景：2026-10 的公式导入修复（提交 `30283ca`）已确认活动链路是 `contentimport.html` + `markdown-import.js`，上述文件全部为历史遗留。删除它们同时缩小仓库与生产静态资源体积，但**必须保留 `markdown-import.js` 与 `contentimport.html`**。

### F16-2：本地 `npm audit` 名存实亡

本机 npm registry 指向 npmmirror 镜像，该镜像未实现 security advisory endpoint（404）。迭代 14 曾在标准 registry 语义下清零漏洞（PostCSS 已 8.5.15），但当前本地环境根本无法执行审计——依赖漏洞门禁只存在于 CI（若 CI registry 配置正确）。缺一条**本地可复现**的审计入口。

### F16-3：生产代码残留 8 处裸 `console.log`

项目已有统一日志工具 `src/utils/logger.js`，但以下文件仍直接调用 `console.log`：`PdfViewer.vue`（3 处）、`ArticleDetail.vue`（3 处，含公式渲染与 PDF 占位符调试日志）、`WriteArticle.vue`（1 处）、`UEditor.vue` 若干 `console.warn/error`。另 `contentimport.html` 对话框内联脚本含调试 `console.log`。调试日志进入生产控制台，既违反项目日志规范也泄漏内部实现细节。

### F16-4：4 个源文件超过 800 行规模上限

| 文件 | 行数 |
|---|---:|
| `frontend/src/views/MathTraining.vue` | 969 |
| `frontend/src/views/ArticleDetail.vue` | 959 |
| `backend_cpp/controllers/AdminController.cc` | 906 |
| `backend_cpp/controllers/ArticleController.cc` | 819 |

超出项目约定（典型 200-400 行，上限 800）。前端两个视图可按职责拆子组件/composable；后端两个控制器可拆 service 层或按路由域拆文件。**拆分属结构重构，须以现有 266 个单测 + E2E + ctest 为安全网**，单独成 Epic 不与功能混做。

### F16-5：后端单元测试覆盖单薄

`ctest` 仅 1 个测试 target（0.57s），对应 36 个 C++ 源文件。前端有 266 个单测，后端几乎全靠 CI 集成测试兜底。核心模块（`core/security.cc`、`core/database.cc`、各控制器的请求校验分支）缺少可本地快速回归的单测。cppcheck 残留 1 个 style 项顺手可修。

### F16-6：`vendor-pdfjs` 1.5MB 全站打包

`pdfjs-dist` 仅被文章详情的 `PdfViewer.vue`（PDF 附件查看）使用，却进入主构建产物。文章详情路由已是独立 chunk，但 pdfjs vendor 仍 1.5MB（gzip 425KB），拖慢需要它的首屏。可通过动态 `import()` 按需加载，仅用户点开 PDF 时拉取。

### F16-7：本机环境遗留进程干扰验证（环境项，非仓库问题）

本机 8888 端口常驻一个 Flask 时代遗留的 Python 进程，服务旧版前端文件，曾在本次公式修复验证中造成"改动无效"的误判。建议清理，并把"端口占用自检"加入项目开发文档。

## 四、迭代目标

1. 删除全部无引用静态死资产，仓库与生产 dist 各瘦身约 2.2MB。
2. 让 `npm audit` 在本地有可复现入口，不再依赖特定 registry 配置。
3. 生产代码日志统一走 `logger.js`，裸 `console.log` 清零。
4. 后端补齐核心模块单测，ctest 从 1 个 target 扩展到覆盖安全/数据库/请求校验主干。
5. 超 800 行的 4 个文件在测试安全网下完成拆分。
6. pdfjs 改为按需加载，降低文章详情首屏成本。
