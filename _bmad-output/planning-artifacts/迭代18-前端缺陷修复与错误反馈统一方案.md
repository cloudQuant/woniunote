## 三、主要发现（重新定性）

### F18-1：错误反馈缺失（#4 + #6，P1，系统性）

**失败路径与用户反馈矩阵（v2 修正版）**

| 失败类型 | 拦截器行为 | 调用方 catch 行为 | 用户实际感知 |
|---|---|---|---|
| **HTTP 4xx/5xx**（后端唯一错误形态） | 构造消息并 reject，**无 ElMessage** | 35 处静默 / 16 处提示 | **多数场景无任何提示**（含登录页） |
| **网络断开** | 同上（"网络错误，请检查网络连接"） | 同上 | 同上 |
| 401 刷新失败（子路径） | 登出 + 跳转登录页 + reject "登录已过期" | 同上 | 跳转可感知，但页面无错误提示 |
| ~~HTTP 200 + code≠200~~ | **当前后端不存在此形态**：`core/response.h` 的 `ok()/badRequest()/unauthorized()` 等辅助函数恒将 body code 与 HTTP status 对齐，`tests/test_response.cc` 专门防漂移。`api/index.js:112-116` 的拦截器 toast 分支为**契约漂移防御**（近乎死代码） | — | 仅契约破坏时出现 |

**修正后的结论**：不存在"业务码错误双重提示"的现实问题（该分支无实例）；唯一且真实的系统性问题是——**所有失败都走 HTTP 错误分支 → 拦截器不弹 → 调用方静默 → 用户无感知**。修复方向不变（方案 A + 静默 catch 补提示），但动机与验收测试全部改为基于真实 HTTP 状态码路径。

### F18-2：批量操作部分失败处理（#5，P1）

`batchChangeType` 使用 `Promise.all`：任一失败 → catch 弹"批量修改失败"（误导：实际部分已成功）→ 不刷新列表。修复：`allSettled` + 三态提示 + 恒刷新。

### F18-3：三项防御性加固（#1/#2/#3，P3）

低触发概率的健壮性问题，各 1-3 行修复 + 单测。注意 #2 的修复代码**必须前置判空**（`new Date(null)` 是合法 epoch 0，会渲染 1970 年——见 A2）。

### F18-4：编辑回填缺回归断言（#7，P2）

功能已修复但现有编辑模式 E2E 只断言 PUT 请求体，无编辑器内容断言。

### F18-5：存量清理缺防增量机制（B2，P1）

静默 catch 清完存量后无任何防线，下一个新视图又会原样引入。盘点脚本须入库并接入 CI 门禁。

## 五、Epic 拆解

### Epic 18.1：错误反馈统一（P1，1 个会话）

**前置结论（已由审阅代跑，直接写入）**：fire-and-forget 审计结果——**无 await/return 的裸 API 调用 0 处；`.then(` 链式调用 0 处**（全仓统一 async/await 风格）。方案 A 无隐藏前置工作量，直接定案。

**方案 A —— 拦截器只做传输层，调用方负责 UX**：

- 错误拦截器**移除业务码错误的 ElMessage**（`api/index.js:112-116` 的 toast 降级为纯 reject；该分支本就是契约漂移防御，移除提示后行为无实际变化）；
- 新增 `src/utils/errorToast.js`：
  - `notifyError(error, fallback)` → `ElMessage.error(error?.message || fallback)`；
  - **启用 ElMessage `grouping`（B6）**：网络瞬断时并发请求（仪表盘类页面 5 个并发、401 排队请求逐个 reject）不产生提示风暴；
- **30 处 API 类静默 catch 改造为 `notifyError`**（清单见附录 A「需改造」组；含登录页 `Login.vue:101`——本迭代最高优先级项）；
- **#6 修法修正（B1）**：reject 侧**不注入通用兜底**，保持 `new Error(data.message)`（message 可能为空串）——这样 `'' || fallback` 自然落到场景化文案，`notifyError` 的 fallback 不被通用文案架空；同时统一拦截器 toast 与 reject 的取值逻辑；
- **改写 `api/index.spec.js` 中钉住拦截器 toast 的用例（A4）**：`:158`（断言 `elMessageError('bad')`）与 `:284`（断言兜底 `'请求失败'`）在移除拦截器提示后必红——改写方向：mock 从 200+code≠200 改为真实 HTTP 状态码路径（400/500），断言点从"拦截器弹提示"改为"reject 的 error.message 正确、由调用方 notifyError 弹出"。

**防增量门禁（F18-5 / B2 / A3）**：

- 盘点脚本 `frontend/scripts/check-silent-catch.mjs` 作为**正式交付物入库**：
  - brace-balanced 解析全部 catch 块，四分类（仅日志 / 刻意忽略 / 表单校验链 / 带提示）；
  - **豁免规则写死在脚本内**：豁免清单见附录 A（非 API 类：编辑器生命周期、MathJax 渲染、localStorage、组件内 error.value 已有 UI 反馈、`validate().catch(() => false)` 表单模式、unmounted 清理等），每条豁免注明文件与理由；
  - 输出「未豁免的静默 catch」数量，>0 时退出码 1；
- 脚本接入 CI（`cpp-vue-ci.yml` 前端 job 增加一步）——「API 类静默 catch = 0」成为持续门禁。

**验收标准**

- 盘点脚本入库并在 CI 运行；全仓未豁免静默 catch = 0；
- 单测（基于**真实 HTTP 路径**）：
  - mock HTTP 500 → 断言 `notifyError` 弹一条提示（代表性视图 3-4 个：Login/Register/Profile/MyDrafts）；
  - 空 message 的 HTTP 错误 → fallback 文案生效（#6/B4，断言空串场景而非 "undefined"）；
  - 并发失败（2 个请求同时 reject）→ 断言 grouping 生效（ElMessage 调用收敛）；
- 现有 443 单测（含改写后的 api/index.spec.js）+ 60 E2E 全绿，覆盖率保持 ≥95/95/95/95。
