## 一、审阅结论与范围调整

原计划覆盖了 CI 修复、浏览器测试、工具链升级和文档，但缺少发布闭环，部分诊断和验收口径需要纠正：

- **凭据治理未闭环**：迭代 19 的实施记录仍明确要求服务器密码轮换，不能概括为“迭代 16–19 已全部闭环”。仓库删除口令不能证明旧口令失效。
- **后端诊断错误**：本轮只读核验 CI 后，首个实质错误是 Drogon 编译缺少 `MYSQL_OPT_NONBLOCK` 等接口，而非 CMake 最低版本拒绝；应追踪实际 MySQL/MariaDB 头文件、客户端库与端口依赖组合。
- **vcpkg 缓存假设错误**：CI 缓存整个 `~/vcpkg`，仅缓存未命中时 clone，并非每次从最新版本库启动。仅添加 override 不能保证所有环境都能解析目标端口。
- **缺少真实部署构建验收**：CI 使用 vcpkg，`scripts/setup_ubuntu.sh` 使用系统库并声明 Drogon 1.9.8 / Trantor 1.5.21。修复 CI 不代表 Ubuntu 部署路径通过。
- **跨浏览器跳过不能直接当作修复**：先区分测试定位/时序问题与产品兼容性问题，再决定修复或有证据的支持范围限制；保留失败用例清单及用户影响。
- **工具链版本组合未验证**：原计划的 `vitest 4 + @vitest/coverage-v8 5` 不应成为实施指令。目标版本必须满足实际 peerDependencies / engines，测试与覆盖率包应匹配。
- **临近发布的大版本升级缺少准入条件**：不把“升级 latest”作为发布成功标准；先恢复可靠门禁，再决定是否纳入本次发行。
- **安装不能稳定复现**：CI 存在 `npm ci || npm install`，启动/部署脚本会删除锁文件。验收必须使用提交中的锁文件，安装失败应暴露出来。
- **Node 约束未贯穿部署**：部署脚本虽然写安装 Node 22，却接受已有 Node >=18；只修改 CI 的 major 版本不足以保证兼容。
- **测试证据边界不清**：Playwright 使用 mock API；HTTP 集成测试没有真实登录全链路，而且未观测到 429 时会 skip。三者不能被概括为真实业务全链路通过。
- **覆盖率路径和含义需修正**：脚本实际为 `backend_cpp/scripts/coverage.sh`；它当前运行 ctest，不能称为全部控制器/HTTP 路径覆盖率。
- **历史文档不能一概归为 Flask**：`docs/迭代1-6` 混有 C++、Vite、Nginx 内容，应逐份标注适用性，而非批量打上 Flask Legacy 标签。
- **缺少发布对象与回滚标准**：需要冻结发布分支、完整 SHA、版本号、Release 内容、交付物、升级步骤和回滚证据；绿灯必须对应将被打 tag 的提交。

### 2.3 后端诊断校正

上述 run 的失败日志显示 Drogon 1.9.11 `MysqlConnection.cc:62:36` 首先报 `MYSQL_OPT_NONBLOCK` 未声明，随后还缺少 `mysql_real_connect_start`、`mysql_get_socket`、`MYSQL_WAIT_*` 等接口。**已确认失败类型为客户端 API/头文件相关编译错误，具体为何选到该接口组合仍待取证。** `CMake Error` / `BUILD_FAILED` 是外层构建错误报告。

[Drogon v1.9.11 顶层 CMakeLists](https://github.com/drogonframework/drogon/blob/v1.9.11/CMakeLists.txt) 已使用 `cmake_minimum_required(VERSION 3.5...3.31)`；[CMake 4.0 说明](https://cmake.org/cmake/help/v4.0/release/4.0.html) 确认移除的是低于 3.5 的兼容策略。这进一步否定了原文对该 run 的直接归因；不能把升级 CMake/Drogon 作为未经定位的默认修复。

[vcpkg 版本规则](https://learn.microsoft.com/en-us/vcpkg/users/versioning) 区分 baseline 和 override；覆盖一个端口也可能改变传递依赖。实施时保存端口版本/port-version、依赖图差异和工具修订，不能只看 manifest 中的一行版本。

本迭代不重写 Git 历史，不重写 UEditor，不顺带升级 pinia/vue-router/pdfjs/eslint 全部大版本，不复活历史 Flask 门禁，不以新增统一框架为目标。允许为已确认的构建、浏览器或发布缺陷进行必要的小范围代码修复；若需要大规模业务重构，另立迭代并重新决定发行范围。
