### 22.1 可信代理限流与验证码资源保护

**地址与限流：**增加专用客户端地址解析，不改变请求真实 peer；校验 IPv4/IPv6、可信代理和头部格式。Nginx 覆盖客户端身份头，非可信直连的伪造头不得改变额度。Redis key 按功能组和规范化地址区分，不存无限长的原始头。超限返回 429 与 Retry-After；受保护组的 Redis 错误、超时和异常返回类型都按 D22-01 返回 503。当前异常返回类型直接放行的分支（`RateLimitFilter.cc:89–95`）须一并覆盖，不能名为 fail-closed 实际仍放行。

**正式配置一致性：**同时调整 `core/config.h` 的默认值及开发/正式配置模板，保留集成配置的一致语义；为已有 `rate_limit_fail_closed=false` 的安装提供显式配置迁移说明。正式配置加载/部署预检发现 false 时给出明确配置错误，切换前保持旧服务可用。用去除凭据后的配置摘要记录加载来源与实际有效策略，不打印完整配置；正式变体在生产等效配置下执行 Redis 故障验证，另测缺省值和显式 false 的拒绝路径，不能由 runner 强行覆盖为 true 后替代这组证据。

生成和独立 verify 计入验证码组；登录请求在认证组和验证码组各计一次，控制器调用校验函数时不得再次扣额度。两组检查共享同一 1 秒截止时间，不能串联两个各 1 秒的等待。不要只给独立 verify 挂过滤器而遗漏实际登录链路；额度耗尽时不得继续消费挑战或进入密码校验。

**限流故障的资源边界：**当前 `runAfter(1.0)` 只结束 HTTP，并不证明 Redis 命令已取消。按 D22-01 限制在途操作；达到上限立即 503，不在应用里无限排队。HTTP 已超时但底层未完成的操作仍占槽，只有固定版本驱动确认完成/取消，或有界的专用连接释放后才能归还。禁止关闭认证共用连接池或无限创建替代连接。用黑洞、迟到响应和恢复实验检查操作数、连接/FD、RSS 及 2 秒回收/5 秒恢复预算；不能以“只响应一次”代替资源回收证明。22.0 先核实固定驱动能力，无法满足时提交替代设计和预算复审。

**验证码：**选定可维护的栅格方案，保持响应字段，图片、日志、DOM 属性和错误响应不携带答案。保留大小写和过期行为；按 D22-02 统一登录与独立 verify 的字段验证和一次消费语义，修正文档中“仅成功消费”的不一致。参数错误、错误答案、正确答案、过期与同一挑战跨入口并发消费分别测试。缓存使用有界容量及有界过期清理，避免每次插入全表扫描；容量耗尽返回可识别的暂时不可用，客户端可重新获取。

验收不以“图片看起来更复杂”为依据。正式变体仍必须没有测试取答案接口；浏览器手动视觉流程与测试注入流程分别报告。

### 22.2 评论删除、级联和计数的一致性

1. 根据 D22-03 统一计数定义；审查用户删除、管理员删除、管理员删用户、隐藏/恢复（若有对应写入口）、文章删除与已有创建路径。不存在的业务入口不额外开发。
2. 权限检查、行锁、实际删除/更新、幸存文章计数维护放在同一事务；检查 affectedRows，重复删除不重复减计数。锁顺序与迭代 21 创建/投票保持一致，涉及多个文章按稳定顺序获取锁。
3. 删用户需覆盖其在他人文章下的评论、根评论消失后不再展示的回复，以及其对幸存评论的投票。按 D22-03 同事务维护 `replycount` 和幸存评论的 `agreecount/opposecount`；被删评论及其投票已一同消失时不再更新不存在的对象。不能仅统计被 FK 物理删除的评论行；隐藏评论仍保存投票与赞踩数。删除文章时文章本身也消失，不给已删除文章重复递减。
4. 明确事务提交确认后才报成功；复用既有未知写入结果契约。COMMIT 回复丢失不能改称“肯定未删”，也不能由客户端自动重发写请求。
5. 提供历史差额的只读报告，以及独立、显式启用的修复命令，分别列出文章评论总数和评论赞踩数的差额。修复前备份、预览影响文章/评论、在事务内重新核对当前状态；不得用过期报告覆盖并发新评论或投票。中断可重跑，实际安装的数据修复另按已批准维护窗口执行。

实现优先保证事务正确性；计数采用受影响行差量还是按文章重算，须结合新索引和基准选择并在设计记录说明。不得使用下限截断把错误计数“修成 0”，也不得用缓存掩盖数据库差额。

**删用户与新增评论/投票必须共同序列化：**不能先枚举目标用户的评论和投票，再允许其向未枚举文章/评论提交新写入，最后由 FK 级联删除而漏掉计数维护。建议以用户行作为共同的事务入口锁，在锁定后枚举受影响文章/评论；创建和投票路径须在获取文章锁前参与同一协议。设计时同时复核删除文章/评论及隐式 FK 锁的顺序；若采用其他方案，须给出等效的并发证明。这里允许为一致锁序调整迭代 21 创建/投票路径，但保留其事务及提交确认语义。强制复现“删除已枚举、创建或投票尝试进入未枚举对象”和相反提交次序，核对幸存文章/评论的三类计数，不仅运行随机并发。

### 22.3 顶层评论与回复的有界分页

**新读取契约：**推荐显式新端点 `GET /api/comments/article/{articleId}/page` 和 `GET /api/comments/{id}/replies`。顶层按 `(createtime DESC, commentid DESC)`，回复按 `(createtime ASC, commentid ASC)`；游标携带版本、所属文章/根评论、排序边界和本次遍历上界。参数非法、超长、跨资源游标须拒绝，所有 SQL 参数化。

**遍历上界与并发语义：**首个根页或回复页在同一 HTTP 请求的一致性读取快照内取得所属文章的 `MAX(commentid)`，空集合记 0，作为该次独立遍历的 `upper_comment_id`；后续游标保留此值，并结合上一页末项的 `(createtime, commentid)` 严格排序边界查询。回复展开另起自己的遍历，不沿用根页的游标。通常后分配且 ID 大于上界的新评论只在刷新后出现；但 ID 或创建时间不等于提交顺序，首屏时尚未提交、之后提交且 ID 不超过上界的行，可能在未经过的排序区间出现，也可能被本次遍历跳过。此类并发变化采用明确的弱一致性，不承诺冻结首屏成员集合；停止写入后重新刷新并完整翻页须无漏重。现有正常写入口不得修改已创建评论的排序键，不引入跨 HTTP 请求持有的数据库事务。

首屏默认只取 20 个根评论及各根的回复数量，不自动取全部回复；展开后独立分页。响应包含 `items`、`has_more`、`next_cursor`，根分页另有文章级 `total_visible`，回复分页另有根级 `total_replies`。总数表示本次读取快照内当前可展示的数据，不按游标遍历上界缩减，也不等于当前页长度；新增/删除后不同 HTTP 响应的总数允许变化。根页总数与文章 `replycount` 在同一读取快照、同一可见性口径下须相等，稳定数据时与独立 SQL 计数核对；不要拿两个并发时刻的值直接判定漂移。没有更多数据时 next_cursor 为空，不用空成功占位掩盖失败。

新增评论端点保持 `{code, message, data}` envelope，并在正常/受控错误响应的 `data.contract` 标识 `comments.v1`。资源不存在或不可见统一返回 HTTP 404、`data.error_code=COMMENT_RESOURCE_NOT_FOUND`，不泄漏隐藏资源身份。前端只有收到匹配合同的资源错误才显示对应不存在提示；无合同标识的 404、HTML 响应或不匹配的成功结构归为协议不兼容/入口异常，显示“评论服务暂不兼容或不可用，请刷新页面后重试”。该提示不宣称已识别服务端版本；401/403、网络和 5xx 仍按各自类别处理。API 错误对象须保留这些字段供评论模块判定，不依赖中文 message 文本分支。

本工作包统一负责 `ArticleComments.vue`、`useArticleComments.js`、`ArticleDetail.vue` 的评论接入及其测试，包括展开/加载更多、投票和回复操作的原生键盘行为、焦点与错误提示。当前 `ArticleDetail.vue:70–86,212–213` 仅传递评论数组与操作状态，`useArticleComments.js:48–56` 读取失败返回 false，而 `ArticleComments.vue:126` 对空数组直接显示“暂无评论”；仅修改 API 错误消息不能满足上述兼容合同。应将首屏加载、成功空集合、已有结果、可重试失败及协议不兼容状态贯通 composable、详情页与评论组件；只有有效合同下成功返回的真实空集合才显示空态。后续页失败保留已加载内容并在对应加载位置提示，评论故障不隐藏文章正文，重试/刷新控件须可键盘操作。触达的仅 click span 改为可聚焦控件；22.5 不并行修改这些评论文件。AC22-13 的评论部分由本工作包交付，最终与文章分页一起验收。

**容量还包括正文：**现有 MEDIUMTEXT 和写入口没有已确认的业务长度上限，不能只限制条数后宣称响应内存有界。建议审阅后将下列值冻结为硬合同：新评论最多 2,000 个 Unicode 码点且不超过 8 KiB UTF-8；列表摘要最多 500 个码点且不超过 2 KiB UTF-8；历史正文分段最多 8 KiB UTF-8；本工作包覆盖的文章评论读取响应最多 1 MiB 序列化 UTF-8 JSON。两类长度限制均校验，不按 JS UTF-16 code unit 误算。范围明确为旧 `GET /api/comments/article/{articleId}`、新 `/page`、`/{id}/replies` 和 `/{id}/content`；`/api/comments/my`、`/api/admin/comments` 的历史长正文治理后移，不在本轮声明相同保证。

历史长评论保留原文，摘要明确标识未展开完整内容；详情通过 `GET /api/comments/{id}/content?cursor=...` 分段获取。分段保持 UTF-8 完整，不在数据库中截断原文。先做有界 SQL 投影再取内容，不先读取整个 MEDIUMTEXT 后截断。摘要、分段和回复端点都重新执行文章、作者/访客、隐藏及父评论可见性检查；持有游标不构成读取授权。超长历史数据、控制字符导致的 JSON 转义膨胀和多字节边界进入回归，最终按实际序列化字节数验证上限。

旧全量入口先做条数/字节预算预检，超过预算返回显式兼容错误，例如 409 + `COMMENT_CLIENT_UPGRADE_REQUIRED`，不把截断后的集合伪装为全量。新旧入口都不能先把整篇评论正文搬入应用再判断大小。小集合继续保留旧数组形状，兼容矩阵写清不同客户端看到的行为。

旧入口的预算预检与取数须使用同一个有界生命周期的一致性读取快照，并对最终序列化大小再次核验；只固定最大 ID 不能解决正文或可见性变化。预检后并发插入/修改不能把实际响应推过预算，也不能使已按旧全量合同返回的数据悄悄少行。无法取得一致快照或超过读取时间预算时明确失败，不拼接不同快照的成功响应；快照只服务本次 HTTP 请求，不延长到用户后续翻页。

| 客户端 / 服务端 | 必须验收的行为 |
|---|---|
| 迭代 21 UI / 迭代 21 后端 | 记录小集合的完整旧数组、根/回复展示和失败反馈；大集合记录实际条数/字节及既有无界行为。此行只要求基线证据齐全，不以本轮分页、刷新提示或容量目标断言旧版通过 |
| 迭代 21 UI / 迭代 22 后端 | 200 条且 1 MiB 以内的旧集合仍返回完整旧数组；超过任一预算返回 409，旧 UI 显示服务端“请刷新页面以使用分页查看”的错误。旧组件在错误后仍可能显示空态，这是原 UI 的已知限制，不能凭后端修改承诺其消失；须刷新到新 UI 才恢复完整评论功能。通过真实旧 UI 记录结果，不能只测新 mock |
| 迭代 22 UI / 迭代 21 后端 | 新端点缺失时按上述无合同响应规则分类，保留文章阅读，评论区显示“评论服务暂不兼容或不可用，请刷新页面后重试”，提供用户触发的整页刷新；不请求旧全量端点、不自动循环刷新、不显示“暂无评论” |
| 迭代 22 UI / 迭代 22 后端 | 完整分页、展开、可见总数、评论写入后定位/刷新符合新契约 |

首次升级和回退须安排刷新旧页面的兼容过渡；上述混合组合是明确的功能降级，不等于无感兼容。D22-04 的推荐决策包含接受旧 UI 的这段过渡限制；若审阅不接受错误后旧空态或要求混合组合仍能完整分页，须先交付客户端桥接版本并重新审阅增加的范围与工期，不能要求冻结的旧代码凭空具备新行为，也不能仅凭旧 hash 资源仍存在就放行。

在 1 千、1 万、10 万条评论及单根高回复数的数据集上核对 EXPLAIN/实际查询、结果量、响应字节、RSS 和 p50/p95。再确定复合索引，不重复堆叠已有单列索引；新增索引有迁移、重跑和回退说明。稳定数据集跨页无漏重；并发新增按上界及迟到提交规则处理，刷新后重新建立遍历；并发删除按当前可见数据跳过，不承诺跨 HTTP 请求的数据库快照隔离。强制构造“首屏前已分配较小 ID 但未提交、另一条较大 ID 已提交、首屏后再提交较小 ID”的时序，分别验证其位于游标前后时的允许行为及稳定后刷新可见性，不仅测试按 ID 顺序提交的情形。

### 22.4 依赖就绪检查与发布判定

1. 保持已有 liveness 路由语义，新增独立 readiness。MySQL/Redis 检查只读、总超时有界，超时和迟到 callback 只响应一次；按 D22-05 合并探测、限制等待者并短时复用结果。Nginx 精确路径按实际入站连接源执行监控 allowlist，未获准请求不转发；后端仅信任本机、精确 Nginx peer 和单独配置的直接监控 peer。后端不能从代理连接反推原监控源，也不以 X-Forwarded-For / X-Real-IP 作为该 ACL 身份。两层分别在依赖探测前拒绝未经允许的源（403）；多层代理需要另行明确可信链，不能自动扩大本机单代理方案。
2. 对外只返回 ready/not_ready 和固定故障类别，响应 no-store；日志用关联 ID 定位，避免把异常原文、连接串或配置放进响应。已有管理员 DB 诊断也按此脱敏。
3. 从直连和真实 Nginx 入口分别断言状态、JSON MIME 和响应结构，避免 SPA fallback 的 HTML 200 被视为健康；不假设公网 `/health` 当前必定代理到后端。
4. **正常发布在停旧服务之前执行预检。** 在持有部署锁、候选静态配置检查完成后，读取旧实例的 readiness；仅已登记的迭代 21 旧候选使用下述受限兼容探针。预检须有总时限并记录对应旧版 SHA、有效配置摘要和结果，禁止复用构建前的陈旧成功。失败即非零退出，不进入切换事务、不安装候选 unit、不停止旧服务、不改 current/rollback 或 Nginx 配置；记录实际服务状态，不承诺本来已经故障的业务恢复。当前 `deploy_release.sh:764–779` 是先开启事务/停止旧服务，候选启动后才检查 health，此前置步骤须显式实现，不能只写在状态表中。它约束正常的新版本发布；显式回滚和已有失败事务的恢复仍走带锁恢复流程，不因当前故障实例无法就绪而禁止恢复。
5. 候选启动后，在现有 release manager 的 verified/committed 前检查 readiness，保留只读业务、静态和持久上传 smoke。新增 readiness 不能替代它们，也不能破坏迭代 21 的恢复时间预算。
6. 不增加未经验证的“自动判定一定是共享故障”逻辑：所有候选就绪失败先沿既有错误处理做一次有预算的旧版本恢复；候选与旧版本都失败时记录两个独立结果，原因保留“依赖或配置待定位”。任何错误都不能进入候选 verified/committed，且不无限自动重启。

**探针超时与资源回收分开管理：**HTTP 超时仅结束当前等待者，不能据此提前释放仍有底层操作的单飞槽。优先验证固定版本驱动的超时/取消语义；必要时使用容量固定的专属探针连接，在 D22-05 的 2 秒预算内确认本地操作结束或连接释放后才允许下一组。不得关闭业务共享连接池，也不得无限创建替代连接。迟到回调绑定探针代际，不能覆盖新结果或重复响应。不能仅凭设置了 `setTimeout` 就认定底层已取消；需以黑洞、迟到回包和恢复实验核对实际在途数、连接/FD 数及恢复预算。无法满足时须修改设计并复审，不能用永久 PROBE_BUSY 或超时后无限重建蒙混过关。

| 场景 | 指针、进程、入口与事务的要求 |
|---|---|
| 正常新发布的切换前旧版本/依赖预检已失败 | 不开启切换事务、不安装候选 unit、不停止旧服务、不切换 current/rollback 或 Nginx；保留旧入口并返回失败，不阻止显式回滚或既有事务恢复 |
| 候选失败，旧版探针与业务 smoke 成功 | 停止候选，恢复旧 current/unit/Nginx 并启动旧服务；只在恢复证据齐全后将事务记 recovered、清除 active 标记；部署命令仍非零退出 |
| 候选和旧版依赖检查都失败 | 尽力恢复旧 current/unit/Nginx/进程；记录每一步实际结果。旧版仍不就绪则事务不记 recovered，保留 active 标记并非零退出；旧入口保持，业务可能仍不可用，不承诺恢复流量，也不发布候选 |
| 恢复指针、配置或启动本身失败 | 保留最后已证实的 phase/active 标记，不虚写 current 已恢复；报告具体未完成步骤，遵守原 60 秒恢复预算 |
| 修复依赖/配置后重试 | 经同一带锁恢复入口幂等恢复旧候选并重新检查；成功才清理 active 标记，随后新发布必须重新发起；不自动继续提交先前失败候选 |

仅对预先登记、绑定完整 SHA 的迭代 21 旧候选允许缺少 ready 路由：由受限本地兼容探针读取该旧版已核验的运行配置，限时执行 MySQL SELECT 1、Redis PING，再运行原业务/上传 smoke。全通过时可标记 `RECOVERED_LEGACY_PROBE`，旧版 readiness endpoint 能力记 `NOT_SUPPORTED`；不是新端点 PASS。配置或探针不可用时保持恢复未完成，不单凭 liveness 清理事务。迭代 22 候选缺失新路由直接失败，不触发此兼容分支。

### 22.5 列表最新结果、键盘分页与编辑错误恢复

- 为 ArticleList 的结果、总数、loading 和错误提示绑定请求代际；取消旧请求可节省资源，但只有当前代际能写状态。组件 catch 必须在调用 `notifyError` 前判断代际；旧请求或卸载后的错误不提示，当前请求失败仍有提示。401 沿用迭代 21 拦截器的会话刷新/失效处理，不能用列表代际逻辑跳过认证。关键词 A→B、分类切换、翻页交错和旧请求错误都需覆盖。
- 将列表状态区分为加载中、成功有结果、成功空集合和可重试失败。建议新查询开始时清除上一查询的结果及总页数（`totalPages`），结果总数置为未知；同步通知 `Search.vue`，不把未知数渲染为“共 0 篇”或沿用 A 的总数。只有当前查询成功返回空集合才显示“暂无文章”；失败显示当前查询的错误和键盘可操作的手动重试。重试仍绑定原查询与当前代际，不自动重写任何数据。
- Pagination 使用具有原生键盘行为的按钮或有真实目的地的链接；补分页标签、当前页 aria-current、禁用状态和可见焦点。本工作包负责文章列表、通用分页和编辑页；评论交互由 22.3 负责，联合完成 AC22-13，不扩成全站重设计。
- 编辑读取区分 401/403/404/网络/5xx。临时错误停留原路由，显示重试；读取成功前避免把空表单误当原文并允许覆盖保存。迟到读取和重试不得覆盖用户已经输入的内容，保留迭代 21 的账号隔离恢复边界。
- 将分类加载、会话初始化和文章读取的就绪条件分别记录；首次进入创建或编辑页时，分类 503/断网不能形成无提示的禁用表单。提供位于 inert 范围之外的可键盘操作重试入口；重试必须绑定当前账号及目标，完成当前模式所需初始化后才解锁，不能仅靠 finally 无条件将表单标为就绪。连续失败保留可恢复状态，迟到成功和目标切换不串稿。
- 组件复用时监测编辑 ID 和创建/编辑模式变化。表单、读取代际、上传回填及提交目标绑定同一账号和文章身份；新目标载入成功之前禁用保存/发布，提交时再次核对目标。A→B、A→B→A、编辑→创建以及 A 读取/上传迟到都须验证；不能只改请求取消而仍按当前 route ID 提交旧表单。未提交内容按 D22-06 保留，不覆盖其他文章的恢复记录。
- 代际判断同时覆盖读取的成功、失败与 finally：B 已成为当前目标后，A 的迟到 404/503/断网不能触发旧错误提示、跳离 B、结束 B 的 loading 或改变 B 的可提交状态；B 自身的错误仍按 D22-06 处理。401 的全局会话失效行为继续沿用迭代 21，不由组件忽略旧响应的规则绕过。

### 22.6 整体验收、证据交付与独立审阅

执行第 5 节矩阵，将失败的首次证据和修复后证据分开；修改范围完成后整体验收一次，只有新变化或未解决问题才扩大重跑。交付一个外部审阅者能打开的脱敏验收包和索引，不能只给会被清理的 `/tmp` 路径。

调整报告保留策略时验证成功和失败分支都上传；使用 manifest 校验候选身份和文件摘要。D22-07 的期限经审阅确认后，读回 CI 配置与平台实际到期元数据；补充归档记录其保存策略和到期时间，并由独立审阅者实际取回、校验摘要。平台保存上限不满足批准周期时，补充归档须覆盖缺失窗口，不只填写一个保存地点。不要求等待整个保存周期结束才验收，也不以配置中写了 retention-days 就声称实际留存有效。

## 9. 技术依据

项目源码是本次发现的主要依据；以下官方资料只用于约束方案，并不证明本项目已按方案实现。查询日期：2026-10-24。

- Nginx 对真实地址替换要求配置可信来源；本方案据此限定代理信任链，而不是无条件采信客户端提供的头。[ngx_http_realip_module](https://nginx.org/en/docs/http/ngx_http_realip_module.html)
- 读后再改相关记录时，普通 SELECT 不能替代需要的锁定读取；具体锁顺序仍要用本项目事务路径验证。[MySQL 8.0 Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)
- PDF.js 的加载任务提供销毁/取消资源的能力；后续方案须对照仓库锁定版本验证，不能照抄最新接口。[PDFDocumentLoadingTask](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFDocumentLoadingTask.html)
- CI 产物支持配置保存期限和下载校验，期限受仓库/组织设置约束；这是证据交付能力，不等于自动满足本项目留存目标。[GitHub Actions artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data)
- 按钮的 Enter/Space 触发和焦点行为应符合交互语义；本轮优先使用原生控件，并通过实际键盘任务验证。[WAI-ARIA Button Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/)
