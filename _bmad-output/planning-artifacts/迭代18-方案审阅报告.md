## 二、A 类发现（开工前必须修正）

### A1.【事实基础错误】F18-1 失败矩阵建立在错误的后端契约假设上

方案的失败矩阵第二行「业务码错误（200+code≠200）→ 拦截器 ElMessage 提示」描述的路径**在当前后端不存在实例**：后端统一响应封装（`backend_cpp/core/response.h`）保证 HTTP 状态码与 body code 恒一致，且 `tests/test_response.cc` 专门防漂移。因此：

- `api/index.js:112-116` 的 `ElMessage.error(data.message || '请求失败')` 分支**几乎是死代码**；
- 「15 处双重提示」是理论风险（仅契约漂移时发生），不是方案所称的现实问题；
- 真实且唯一的系统性问题：**所有失败都走 HTTP 错误分支 → 拦截器不弹 → 调用方静默 → 用户无感知**。

**对方案的影响**：Epic 18.1 的修复方向（方案 A + 静默 catch 加提示）**依然成立**，但以下内容必须重写：

1. 失败矩阵改为两行：HTTP 4xx/5xx、网络断开（删除「业务码错误」行，或注明"仅契约漂移时存在"）；
2. 验收标准「业务码失败仅一条提示」的单测改为基于真实路径：mock HTTP 400/500 → 断言 `notifyError` 弹一条提示；
3. 「消除双重提示」从目标中移除或降级为契约防御性说明。

不修正的后果：18.1 的测试计划会围绕一个不存在的路径设计用例，验收「各有一个代表性单测」形同虚设。

### A2.【提议代码缺陷】`formatTime` 修复代码对 `null` 输入会渲染 1970 年

方案提议 `const d = new Date(iso); return Number.isNaN(d.getTime()) ? (iso || '-') : d.toLocaleString('zh-CN')`。**`new Date(null)` 是合法的 epoch 0**（不是 Invalid Date），`getTime() === 0` 非 NaN → 走 `toLocaleString` → 用户看到「1970/1/1 08:00:00」。

更糟的是，方案的单测清单（合法 ISO / undefined / 非法字符串）**恰好漏掉 null**——唯一能暴露此 bug 的用例。修正：

```js
if (!iso) return '-'
const d = new Date(iso)
return Number.isNaN(d.getTime()) ? (iso || '-') : d.toLocaleString('zh-CN')
```

单测增加 null 用例。（`created_at` 虽 NOT NULL，但防御性修复不应自带新边界 bug。）

### A3.【统计失准 + 验收不可判定】35/15 数据不可复现，「盘点脚本输出 0」缺乏判定基础

独立盘点结果为 **50 静默 / 16 带提示**（含 composables/stores/utils/components/views 全量）。差距并非小事：`useArticleComments.js` 一个文件就有 5 处 **API 类**静默 catch（获取评论 `:48`、发表评论 `:68`、回复 `:113`、点赞 `:133`、反对 `:151`——全部只 `console.error`），若方案的"约 31 处"清单基于 views+components 统计，这 5 处会被整体遗漏。

同时，验收标准「全仓静默 catch（API 类）清零：盘点脚本输出为 0」依赖一个**尚不存在、归类规则未定义**的脚本——哪些 catch 属于「API 类」、哪些豁免（UEditor destroy ×5、MathJax 渲染 ×2、theme ×3、logger ×3、refresh token ×1……），直接决定输出是否为 0。当前状态下该验收标准**不可判定**。

**修正要求**：

1. 方案附录给出完整的 file:line 清单（静默 API / 静默非 API / 带提示三类），消除 35 vs 50 的歧义；
2. 盘点脚本升级为 18.1 的正式交付物（提交入库），归类规则（豁免清单）写进脚本本身；
3. 参见 B2：脚本应进 CI 门禁，否则只清存量不防增量。

### A4.【任务遗漏】移除拦截器 ElMessage 会反向破坏既有单测

`api/index.spec.js:158` 断言拦截器对 code≠200 弹 `elMessageError('bad')`，`:284` 断言兜底 `'请求失败'`。Epic 18.1 移除拦截器提示后，**这两个用例必红**。方案在 18.2 中记得「同步更新 ArticleCategoryCenter.spec.js 中钉住旧行为的用例」，却在 18.1 对自己的拦截器测试只字未提。须在 18.1 任务清单中补上「改写 `api/index.spec.js` 中钉住拦截器 toast 行为的用例」（改写方向见 A1：顺带把 mock 从 200+code≠200 改为真实 HTTP 状态码路径）。

### A5.【研究产物未清理 + E2E 计数失真】`_probe7.spec.js` 会被 E2E 门禁拾取

- `playwright.config.js:52-53`：`testDir: './e2e'`，`testMatch: '**/*.spec.js'`，**无 testIgnore** → untracked 的 `frontend/e2e/_probe7.spec.js` 会被 `npm run test:e2e` 拾取执行；

## 三、B 类发现（建议修正）

### B1. `notifyError` 场景化 fallback 与 #6 修复互相抵消

#6 修复（reject 改为 `new Error(data.message || '请求失败')`）使 `error.message` **恒非空**，于是 `notifyError(error, fallback)` 中 `error?.message || fallback` 的场景化 fallback **永远不会触发**——两个机制重叠，方案声称的「列表类失败用场景化 fallback」成为死代码。须明确优先级，建议二选一：

- reject 侧不注入通用兜底（message 可能为空串，`'' || fallback` 自然落到场景文案）——**推荐**，职责最清晰；
- 或 `notifyError` 识别到通用文案 `'请求失败'` 时改用 fallback。

### B2. 缺少防回归机制，静默 catch 会重新积累

方案清完存量（50 处）后没有任何增量防线。下一个迭代写新视图时，`catch (e) { console.error(e) }` 又会原样出现。建议：A3 的盘点脚本接入 CI（或引入 ESLint 规则，如自定义 `no-silent-catch` 搭配豁免注释），把「API 类静默 catch = 0」变成持续门禁而非一次性清理。

### B3. #5 现状描述不精确，影响测试断言设计

`batchChangeType` 的 catch 并非「直接返回」——`ArticleCategoryCenter.vue:285` 会弹 `error.message || '批量修改失败'`。真实缺陷是：部分失败时该提示**误导性地声称全部失败**（而实际部分已成功）+ 列表不刷新。修复方案（allSettled + 三态提示 + 恒刷新）正确，但「现状无提示」的错误认知可能让实施者低估用户现状（用户目前会收到一条错误 toast，只是内容错误）。18.2 的单测应对「现状提示文案误导」这一行为变化有明确认知。

### B4. #6 的「undefined」症状描述错误，照此写单测会失败

实际症状是**空字符串**（`new Error(undefined).message === ''`；若后端显式返回 `message: null` 则是 `"null"`）。单测断言应为「空 message → fallback 文案生效」，而非断言字符串 `"undefined"`。

### B5. 上传 URL 声明应以通道为限

「后端上传返回的 URL 恒为 `/api/uploads/xxx.pdf`」仅对 UEditor 富文本通道成立；独立 `uploadApi`（头像/图片/文件）返回 `/static/uploads/...`。正文 PDF 场景结论成立（富文本内插入的文件走 UEditor 通道），新选择器 `a[href*="/api/uploads/"]` 不覆盖 `/static/uploads/*.pdf` 与现状一致、非回归——但方案应把声明限定为「富文本通道」，避免后续迭代误把 `/static/` 通道的 PDF 也期待被转换。

### B6. 未考虑并发失败的提示风暴

改造后每个调用方 catch 各自 `ElMessage.error`：网络瞬断时仪表盘类页面并发 5 个请求 = 5 条相同 toast 叠加；401 刷新失败时排队请求逐个 reject 亦然。建议 `notifyError` 内启用 ElMessage `grouping`（或同文案节流），成本一行，避免改造引入新的 UX 问题。

### B7. fire-and-forget 审计应前置，且结果已知

方案把 A/B 取舍的决定性输入（fire-and-forget 审计）推迟到实施阶段。本次审阅已代跑：**无 await/return 的裸 API 调用 0 处；`.then(` 链式调用 0 处**（全仓统一 async/await 风格）。风险可判定为极低——建议直接把该结论写进方案，A/B 之争随之消解（方案 A 无隐藏前置工作量）。
