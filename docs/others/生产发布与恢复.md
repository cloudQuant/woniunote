# 生产发布与恢复

生产版由 `scripts/deploy_release.sh` 管理。`start_app.sh prod`、`restart_app.sh prod`、`stop_app.sh prod` 和 `scripts/setup_ubuntu.sh` 都经过同一把 `flock` 锁。setup 从安装/数据库准备开始一直持锁到最终发布；其内部调用依据 Linux `/proc/locks` 中锁文件身份和持锁进程祖先链复用锁，普通环境变量不能伪造这个关系。新版本先从精确 Git commit 构建前后端并校验候选 Nginx 配置，之后才停止旧服务。

## 发布前配置

Ubuntu 初始化完成后，在部署目录的 `.woniunote-deploy.env` 中设置 smoke 和兼容性证据路径。初始化脚本首次创建此文件时权限为 `0600`；如果文件已经存在，初始化脚本不会覆盖它。文件按逐行 `KEY=value` 读取，不要在值外加 shell 引号。配置文件自身不要写入日志或提交到 Git。

至少提供一个实际存在、保存在共享数据目录中的上传样例，供切换前检查本地 SHA-256、切换后通过 Nginx 读取并再次核对内容：

```text
WONIUNOTE_SMOKE_UPLOAD_PATH=/api/uploads/deploy-smoke.txt
WONIUNOTE_SMOKE_UPLOAD_FILE=/path/to/backend_cpp/uploads/deploy-smoke.txt
WONIUNOTE_SMOKE_UPLOAD_SHA256=<该文件的64位小写SHA-256>
```

`WONIUNOTE_SMOKE_UPLOAD_FILE` 必须位于 `WONIUNOTE_DATA_DIR` 下，URL 必须是 `/api/uploads/...` 或 `/uploads/...`。样例文件需要由运维人员预先放入持久目录并确认可公开读取；部署程序只读取它，不创建、覆盖或删除它。未配置、文件不存在或摘要不匹配会在停止旧服务前拒绝发布。只读 API 和缩略图 smoke 的默认路径分别是 `/api/articles/types` 和 `/api/thumb/1.png`；可用 `WONIUNOTE_SMOKE_READONLY_API`、`WONIUNOTE_SMOKE_THUMB_PATH` 指定站点上已验证可用的路径。`WONIUNOTE_SMOKE_HOST`、`WONIUNOTE_SMOKE_SCHEME`、`WONIUNOTE_SMOKE_PORT` 用于本机回环探测；显式设置端口时它也会写入请求 URL。

每次升级都需要一份绑定旧、新 Git SHA 的兼容性记录；首次从旧式安装切换时，记录的旧 SHA 也必须准确对应旧版本。回滚需要单独配置反向记录。记录格式如下，所有 `PASS` 必须来自相应 SHA 的实际检查，不能用模板或占位结论代替：

```text
FROM_SHA=<当前运行版本的完整 Git SHA>
TO_SHA=<候选版本的完整 Git SHA>
API=PASS
SESSION=PASS
SCHEMA=PASS
OLD_FRONTEND_NEW_BACKEND=PASS
NEW_FRONTEND_OLD_BACKEND=PASS
EVIDENCE=/path/to/compatibility-evidence.txt
EVIDENCE_SHA256=<证据文件的64位小写SHA-256>
```

将路径分别写入 `WONIUNOTE_COMPATIBILITY_RECORD` 和 `WONIUNOTE_ROLLBACK_COMPATIBILITY_RECORD`。发布管理器会校验 SHA、状态字段和证据摘要；它只验证记录的完整性，不会代替 API、会话、数据库 schema 或前后端混合版本兼容测试。

如果没有当前 release 且服务已停止，首次安装还必须提供 `WONIUNOTE_INITIAL_INSTALL_RECORD`。这项检查同样覆盖直接 deploy、start/restart 及 setup 入口，并在构建前执行。记录必须是 root 持有的 `0600` 普通文件，不能是符号链接；以下维护模式示例中的状态只能在对应证据完成审阅后填写：

```text
TO_SHA=<候选版本的完整Git SHA>
MODE=maintenance
REVIEWED=PASS
EDITOR_HANDOFF=PASS
WRITE_FREEZE=PASS
BACKUP_RESTORE=PASS
SCHEMA=PASS
EVIDENCE=<已审阅维护证据普通文件的绝对路径>
EVIDENCE_SHA256=<该证据文件的64位小写SHA-256>
```

全新且没有历史业务数据的实例使用 `MODE=fresh`，保留 `TO_SHA`、`REVIEWED`、`EVIDENCE`、`EVIDENCE_SHA256`，用 `FRESH_INSTANCE=PASS` 替换四个维护状态字段；两种模式的字段不能混用。缺失、重复、未知字段或摘要不匹配会拒绝安装。记录只证明所引用材料未被替换，不能自动证明停写、恢复演练或人工审阅已经完成。已有业务数据的停机实例必须使用维护模式。

迭代 21 的首次升级还需要显式执行已审阅的数据库迁移：训练答案列、投票表以及 `article.thumbnail` 的 nullable `VARCHAR(30)` 到 `VARCHAR(512)` 扩列。流程和支持的旧状态见 [迁移说明](../../scripts/sql/migrations/README.md)。先在恢复副本验证、停写并备份，再按批准的维护步骤迁移；启动脚本和 release manager 不会自动替操作人员修改已有库。封面列过短时安装预检应停止，不能把列名存在视为兼容。

封面升级的 `SCHEMA=PASS` 还须证明 NULL/旧值及字段字符集保留、迁移可重跑，以及真实上传→保存草稿→编辑更换→公开读取的 URL 与图片字节一致。首次原始 v2 只保留应急降级用途；正常回滚版本须已经支持完整上传 URL 和扩列后的 schema，不以静态资源仍存在或数据库可以读取替代业务兼容验收。

运行配置从 `WONIUNOTE_RUNTIME_CONFIG` 读取。发布时按内容 SHA-256 写入 `$WONIUNOTE_DATA_DIR/config-revisions/<digest>.json`，目录权限为 `0700`、快照文件为 `0600`。每个 release 只保存配置引用和摘要；运行中的候选、回滚版本都读取自己绑定的不可变快照。共享配置快照不会随 release 或静态资源清理删除。

## 发布、状态和回滚

首次从旧式安装迁移时，旧二进制、前端 dist、运行配置和 Nginx 主配置会先生成 legacy 回滚版。旧 Nginx 配置必须自包含（仅允许 MIME types include），且每个 root/alias 必须指向旧项目 frontend/dist 或共享数据目录；已知项目 dist 路径会改写为 legacy release 内的冻结副本，并在停旧服务前重新执行 nginx -t。遇到其他 include、未知 root/alias 或校验失败时迁移会拒绝切换。setup 的 rsync 会排除旧 frontend dist、后端 build、上传和缩略图目录，以免在迁移建立回滚快照前覆盖运行文件或持久数据。

发布前从可审阅的 commit 获取完整 SHA，并确认兼容性记录针对同一对 SHA：

```bash
git rev-parse HEAD
bash scripts/deploy_release.sh deploy --sha FULL_COMMIT_SHA
bash scripts/deploy_release.sh status
```

`restart_app.sh prod` 使用调用时的 `HEAD`，而直接调用 `deploy --sha` 可固定候选 commit。部署构建从 `git archive` 读取指定 commit；未提交的工作区改动不进入候选。

发布切换有单一锁和阶段 journal。失败、TERM 或 INT 会尝试恢复旧 current 指针、旧 systemd unit、旧 Nginx 配置和原服务状态；SIGKILL 等无法运行 trap 的中断会留下 journal，下次受锁保护的 `deploy`、`start`、`stop`、`rollback` 或 `gc` 会先尝试恢复。若恢复本身失败，journal 会保留供下一次重试，检查 `status` 输出并查看事务目录中的阶段清单。不要手工删除 active journal 或改写 current/rollback 符号链接。

```bash
bash scripts/deploy_release.sh rollback
bash scripts/deploy_release.sh gc
```

部署切换的停服预算默认最多 10 秒，候选切换失败触发恢复的总窗口为 30 秒，恢复预算最多 60 秒。健康检查、smoke、systemd 操作和 Nginx 检查/重载受绝对 deadline 约束。超过预算会失败并保留恢复状态；这不是对主机负载下实际服务恢复时间的生产证明。

## 文件保留和缓存

发布状态默认位于 `/var/lib/woniunote`，共享业务数据默认位于部署项目的 `backend_cpp/`。release 目录和 hash 资源位于状态目录；上传、缩略图、构建日志和 runtime config revisions 位于共享数据目录。部署会将候选版本中已有的持久目录文件逐项复制或比对 SHA-256，再将候选目录替换为共享目录链接；同名但内容不同的持久文件会使候选失败。release/GC 不会清理共享上传、缩略图、日志或配置快照。

current、rollback 和退休时间尚未超过七天的版本及其 hash 资源会被保留。退休时间在成功切换提交时记录，避免把构建时长算进保留期。Nginx 模板仅对成功响应的带内容 hash `/assets/` 文件设置一年 immutable 缓存；index 与非 hash URL 要求重新验证，缺失资源由 Nginx 返回 404。API 和上传路由仍优先代理到后端。

候选预检解析 `index.html` 引用的本地入口 JS/CSS，要求它们是具有内容 hash 文件名的实际文件，并绑定资源清单中的 SHA-256。切换后的 smoke 会比对首页原始字节，并逐个下载入口 JS/CSS 校验摘要。因此，缺失样式或以 HTTP 200 返回 HTML fallback 也会使发布失败并触发恢复，不能仅凭状态码判定静态资源可用。

## 验证边界

本机可运行隔离的 mock 事务测试：

```bash
bash scripts/tests/test_deploy_release.sh
```

它覆盖锁竞争、构建与切换故障恢复、信号/journal 恢复、多版本保留、回滚、配置快照以及持久数据保护。测试用 mock systemd、Nginx 和 curl，不证明真实 Nginx 缓存响应、Linux systemd 行为或生产可用性。真实 Ubuntu/Nginx 隔离运行时测试见 `scripts/tests/iter21-deploy-runtime/README.md`；该测试的合成兼容性输入也不构成 D04 业务兼容验收。每次发布仍需把真实兼容性证据和运行环境验收结果分别记录。
